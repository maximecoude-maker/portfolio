# CATS — brief source archivé

Contexte fourni par Maxime pour la création de la page. Archive historique : les précisions ultérieures et les réserves de la mémoire projet font foi en cas de contradiction.

---

Tu travailles sur mon portfolio de Senior Product Designer UX/UI.

Je veux que tu crées un projet / case study dédié à mon expérience chez Crédit Agricole Technologies & Services (CATS).

L’objectif n’est surtout pas de produire une page de portfolio UX classique du type :

Research → Wireframes → UI → Prototype.

Je veux une page qui démontre une posture Senior Product Designer, capable de travailler sur un produit à très grande échelle, dans un environnement complexe, réglementé, multi-canal et fortement dépendant de règles métier.

⸻

1. OBJECTIF DU CASE STUDY

Le case study doit raconter comment, pendant près de 3 ans, j’ai contribué à transformer l’expérience liée aux cartes bancaires et services associés chez Crédit Agricole Technologies & Services.

Mon rôle doit apparaître comme :

* Product Designer senior
* capable de cadrer des problématiques produit complexes ;
* structurer une architecture d’expérience ;
* conduire de la continuous discovery ;
* concevoir des parcours critiques ;
* collaborer avec PO, BA, métiers, designers, développeurs, accessibilité et Design System ;
* arbitrer entre besoins utilisateurs, règles métier, sécurité, réglementation et contraintes techniques ;
* rester hands-on sur UX, flows, wireframes, UI, prototypes et tests.

Le récit doit démontrer ma capacité à penser un système produit, pas uniquement à produire des interfaces.

⸻

2. CONTEXTE CATS

Entreprise :
Crédit Agricole Technologies & Services

Produit :
écosystème digital Crédit Agricole, notamment :

* NPC
* application Ma Banque
* PUC

IMPORTANT :

Mon périmètre a évolué dans le temps.

Phase 1 — NPC

Mon intervention était initialement principalement centrée sur le NPC.

J’y ai travaillé sur la transformation des parcours de gestion des cartes :

* liste des cartes ;
* détail d’une carte ;
* sélection entre plusieurs cartes ;
* verrouillage temporaire ;
* plafonds ;
* options ;
* paramètres ;
* opposition ;
* informations carte ;
* assurances et garanties ;
* services associés.

Phase 2 — Ma Banque

Progressivement, mon périmètre s’est étendu à l’application Ma Banque.

L’objectif était notamment d’assurer une continuité entre web et mobile et de rapprocher plusieurs expériences cartes et paiements dans un écosystème plus cohérent.

J’ai notamment travaillé sur :

* Univers Carte mobile ;
* ePIN ;
* cartes virtuelles ;
* opposition ;
* conformité accès mineur ;
* renouvellement e-commerce ;
* Apple Pay / In-App Provisioning ;
* Paiement Mobile / CA Pay ;
* Click to Pay.

Phase 3 / parallèle — PUC

J’ai également travaillé sur le PUC, le portail collaborateur utilisé par les conseillers en agence.

Le PUC représente notamment le pendant conseiller de plusieurs solutions proposées en selfcare sur NPC ou Ma Banque.

C’est un point important du case study.

Il faut montrer que je ne pensais pas uniquement :

“Que peut faire le client seul ?”

mais également :

“Que se passe-t-il si le client demande de l’aide à un conseiller ?”

Objectif :

maintenir une cohérence entre :

selfcare client ↔ accompagnement conseiller

et éviter les ruptures de compréhension entre les canaux.

7. DÉCISIONS PRODUIT À RACONTER

Le cœur du case study doit être constitué de décisions produit, pas uniquement de livrables.

Créer 4 à 6 blocs structurés ainsi :

Problème → Hypothèse → Décision → Validation / apprentissage

⸻

Décision 1 — Faire de la carte le pivot de l’expérience

Problème :

Les fonctionnalités étaient historiquement dispersées et l’utilisateur devait parfois comprendre l’organisation interne du système.

Décision :

Organiser l’expérience autour de la carte sélectionnée :

liste des cartes → carte → actions principales → paramètres/services

Objectif :

permettre à l’utilisateur de savoir immédiatement :

* quelle carte il gère ;
* son statut ;
* ce qu’il peut faire ;
* où trouver les services secondaires.

⸻

Décision 2 — Hiérarchiser actions essentielles et secondaires

Actions principales :

* verrouiller ;
* consulter les informations ;
* plafonds ;
* certaines actions contextuelles.

Actions secondaires regroupées dans Paramètres / services.

Les tests ont régulièrement confirmé que les utilisateurs cherchaient naturellement les actions secondaires dans Paramètres.

⸻

Décision 3 — Concevoir les exceptions dès le départ

Cas importants :

* plusieurs cartes ;
* plusieurs comptes ;
* compte joint ;
* mineur ;
* carte expirée ;
* carte opposée ;
* carte verrouillée ;
* carte virtuelle ;
* restrictions d’éligibilité.

Message :

Nous ne concevions pas une page fixe, mais un système capable de se recomposer selon le contexte utilisateur.

⸻

Décision 4 — Utiliser la recherche pour arbitrer

Exemples concrets :

Carte expirée

Au début des recherches, la combinaison couleur rouge / pictogramme pouvait faire penser à :

* une carte opposée ;
* une alerte ;
* une carte volée.

→ travail sur statut, wording et hiérarchie.

“7 jours glissants”

Terme bancaire régulièrement mal compris.

Certains utilisateurs pensaient :

les 7 prochains jours.

→ besoin d’un affichage plus explicite / date à date.

Carte virtuelle

Très bien comprise pour :

paiement en ligne.

Beaucoup moins évidente pour :

paiement en magasin.

→ besoin de pédagogie autour du Wallet et d’un CTA explicite.

Opposition

Parcours compris mais jugé parfois trop long dans une situation d’urgence.

→ réfléchir en logique :

mode urgence / raccourcissement / meilleure hiérarchie SOS.

9. ePIN

Prévoir éventuellement un focus dédié.

Objectif :

permettre à un utilisateur de consulter son code PIN de manière sécurisée.

Recherche :

* compréhension immédiate ;
* sécurité ;
* consultation visuelle ;
* consultation audio ;
* accessibilité.

Résultats :

* “Voir le code” préféré ;
* Securipass rassurant ;
* confusion possible entre code SMS et code PIN ;
* audio utile pour l’accessibilité ;
* attention à la confidentialité en espace public.

Accessibilité :

travail autour notamment de :

* RGAA 4.10 ;
* RGAA 4.11 ;
* RGAA 4.12 ;
* restitution audio ;
* contraintes techniques Thales.

10. CARTES VIRTUELLES

J’ai travaillé sur :

CVE

Carte virtuelle temporaire / dépannage.

Usage principal :

continuer à payer après opposition, en attendant une nouvelle carte.

CVP

Carte virtuelle permanente.

Enseignements :

usage online très clair.

Usage magasin :

moins évident.

Besoin :

* expliquer Wallet ;
* ajouter au Wallet ;
* distinguer paiement online / magasin ;
* réduire les explications trop longues.

11. ACCÈS MINEUR

J’ai travaillé sur les règles de gestion permettant de distinguer :

* actions accessibles au mineur ;
* actions contrôlées par le parent.

Les restrictions étaient globalement comprises et acceptées.

Besoin identifié :

* feedback clair ;
* mécanisme de demande ;
* notification parent ;
* statut visible.

Exemple :

Carte verrouillée — seul votre parent peut la déverrouiller.

⸻

12. OPPOSITION SELFCARE

Travail sur un parcours permettant de mettre une carte en opposition sans appeler systématiquement un conseiller.

Résultats :

parcours compris et rassurant.

Mais :

dans une situation de vol/perte, les utilisateurs attendent :

* rapidité ;
* signalétique SOS ;
* peu d’étapes.

Pistes :

* parcours raccourci ;
* mode urgence ;
* CTA plus explicite ;
* transparence sur remplacement / délai / frais ;
* modification adresse directement dans le flow.

⸻

13. CARD ON FILE / RENOUVELLEMENT E-COMMERCE

Service permettant la mise à jour automatique des données de carte auprès de certains e-commerçants lors du renouvellement d’une carte.

Enseignements importants :

La simplicité du parcours était bonne.

Mais la confiance était plus fragile.

Problèmes :

* wording trop technique ;
* quantité de texte ;
* manque de visibilité sur les commerçants concernés ;
* inquiétude sur la transmission des données ;
* compréhension insuffisante de la réversibilité du consentement.

Il faut montrer ici une problématique Product Design intéressante :

une expérience peut être simple à utiliser tout en restant difficile à accepter.

15. DESIGN SPRINT PAIEMENT MOBILE / CA PAY

Créer une section dédiée.

Design Sprint :

19, 20 et 21 mai 2026

Sujet :

reprise de Paiement Mobile CA dans Ma Banque.

Contexte :

Paiement Mobile CA était une application distincte.

Problèmes observés :

* expérience fragmentée ;
* activation / configuration complexe ;
* réinstallations ;
* adoption faible ;
* préférence forte pour Apple Pay ;
* coût iOS important.

Data connue :

Paiement Mobile CA environ :

29 % d’utilisation

vs environ :

96 % Apple Pay

dans le contexte étudié.

Objectif :

imaginer une expérience intégrée à Ma Banque.

Méthode :

Jour 1

Comprendre & cadrer :

* Lean Canvas ;
* benchmark ;
* data ;
* Experience Map ;
* How Might We.

Jour 2

Idéation / convergence :

* 5 Why’s ;
* Big Idea ;
* Idea Wall ;
* user flow ;
* wireframes.

Jour 3

Prototype & tests utilisateurs.

Résultats du prototype :

* 3/4 trouvent l’accès plus simple grâce à l’intégration Ma Banque ;
* 4/4 trouvent l’enrôlement simple, fluide et rassurant ;
* logique de sélection des cartes parfois mal comprise ;
* “Activer par défaut” incompris ;
* NFC trop technique ;
* besoin d’un tutoriel d’utilisation ;
* cashback insuffisamment compris.

Vision issue du sprint :

deux moments fondamentaux :

Enrôlement
et
Paiement

Insight central :

Réduire le nombre d’étapes jusqu’au premier paiement est le principal levier d’amélioration.

17. DESIGN SYSTEM MUESLI

Créer une section dédiée au Design System.

Design System :

Muesli — Crédit Agricole Technologies & Services

Je travaillais dans un environnement fortement structuré par le Design System.

Composants / patterns connus :

* Primary button ;
* Secondary button ;
* Link ;
* Chips ;
* Bottom sheet ;
* Button keyboard ;
* navigation ;
* formulaires ;
* tableaux ;
* data visualisation ;
* parcours tunnel.

Règles importantes :

Primary button

* une seule action principale par page ;
* plutôt en bas de page ;
* wording concis ;
* verbe à l’infinitif ;
* maximum environ 20 caractères ;
* pas de point final.

Secondary button

* action secondaire ;
* ne doit normalement pas être seul ;
* cohérence de largeur avec Primary ;
* spacing 32px.

Documentation Muesli :

* aperçu ;
* specs ;
* tokens ;
* states ;
* guidelines UX/UI ;
* UX Writing ;
* animation ;
* accessibilité.

Accessibilité prise en compte :

* RAAM / RGAA selon périmètre ;
* contrastes ;
* éditorial ;
* VoiceOver ;
* zoom 200 %.

Message important :

Je ne “dessinais pas un nouveau composant” par défaut.

Je cherchais d’abord :

comment résoudre le problème avec le système existant.

Puis seulement si nécessaire :

challenger ou faire évoluer le pattern.
